# 架构设计（ARCHITECTURE）

## 总览

```
┌───────────────┐   REST(搜索/点歌预取/歌词)   ┌──────────────────┐    weapi/公开API    ┌─────────────┐
│  微信小程序 A  │ ───────────────────────────▶ │  服务端 (Node.js) │ ──────────────────▶ │ 第三方音乐源 │
│  微信小程序 B  │ ◀──── WebSocket(房间会话) ── │  REST + WS Hub    │ ◀────────────────── │  QQ / NCM   │
└───────────────┘   state/chat/sys/error 下行   └──────────────────┘                     └─────────────┘
```

- **服务端是唯一权威**：房间成员、播放时钟、点歌队列、聊天记录都在服务端；客户端只做渲染与上报。
- 小程序端原生框架开发（无跨端依赖），服务端仅依赖 `ws`，全部基于 Node 内置模块，部署面积极小。

## 服务端分层

| 层 | 位置 | 职责 |
|----|------|------|
| 入口 | `src/index.js` | 装配、监听、优雅停机 |
| 组装 | `src/app.js` | `createApp()` 工厂（集成测试直接注入端口 0） |
| 配置 | `src/config.js` | 环境变量解析 + 启动期校验（fail fast） |
| 房间 | `src/room/room.js` | **纯逻辑状态机**：成员/权限/播放时钟/点歌队列/聊天，时间可注入 |
| 房间 | `src/room/manager.js` | 房间注册表：建房、邀请码索引、空闲清理 |
| 实时 | `src/ws/hub.js` | 会话生命周期、心跳、限流、**合并广播**、播放地址异步解析 |
| 实时 | `src/ws/protocol.js` | 上行白名单校验 + 下行消息构造 |
| HTTP | `src/http/rest.js` | 建房/加入/预览/搜索/歌词/取流/健康检查 |
| 音源 | `src/music/provider.js` | Provider 门面：搜索降级链、跨源播放地址解析、TTL 缓存 |
| 音源 | `src/music/providers/*` | `qqmusic` / `netease` / `mock`（测试） 三个适配器 |

## 播放同步模型（核心）

服务端权威状态：`playback = { track, status, startAtSec, startedAtMs, url }`

```
有效进度(t) = startAtSec + (status=playing ? (t - startedAtMs)/1000 : 0)
```

- 新曲进入 `loading`；客户端 `canplay` 并 seek 到起点后上报 `ready`，首个 ready 建立 `playing` 时间线。
- 暂停、恢复和用户 seek 会重建 `startAtSec + startedAtMs` 锚点并广播；客户端只在锚点变化时立即对齐。
- 稳定播放期间以本地音频时钟为真相，不用周期快照做硬 seek，避免网络抖动被放大成可听见的跳变。
- 曲目自然播完：客户端上报 `end + trackId`；收齐活跃端或首个 end 后 3 秒兜底再接歌。
- 播放地址集中解析：点歌/切歌时 Hub 异步调 Provider 取流，成功后随 `state` 下发 url；**双端永远播放同一个 URL**。失败自动跳下一首并广播系统提示，房间不停摆。
- **音质是房间级设置**（standard 128k / high 320k / lossless FLAC·走自有 VIP 权益）：双端必须同源同文件才能同步，因此音质不属于单端。切换时服务端清空当前曲目 url 并按新档位（参与取流参数与缓存键）重新解析，客户端在同一进度点无缝换源。

## 音乐源策略

1. **搜索/歌词主源**：QQ 音乐公开 Web API（游客可用，元数据与歌词质量最好）。
2. **播放地址解析链**：`曲目自身来源 → qqmusic(vkey 游客) → netease(跨源按"标题+歌手"匹配)`。
3. 实测（2026-09）：QQ 游客 vkey 对 VIP 曲目返回空，网易云旧版接口对热门曲目取流覆盖 6/6（含 VIP 曲，部分为低码率试听段）；因此跨源降级是**必要路径**而非锦上添花。
4. 所有结果走 TTL-LRU 缓存（搜索 10min / 地址 20min / 歌词 24h）；`mock` 源仅供测试，**禁止降级到真实源**（集成测试零外呼）。

## 可靠性与安全设计

- WS：8KB 消息上限、hello 5s 握手超时、ping/pong 心跳（2 周期无响应断开）、指数退避自动重连（客户端）；云 WS 不可用时自动降级 HTTP 轮询，轮询成员用 15 秒在线租约。
- 频控：聊天 6 条/2s、点歌 8 首/10s（按 房间+用户 维度），搜索 60 次/min（按 IP）。
- 广播合并：80ms 窗口内同房间状态只广播一次（**不带 exclude**，避免合并窗口吃掉其他成员的唯一一次广播——集成测试曾抓出此缺陷）。
- 优雅停机：SIGINT/SIGTERM → 停心跳 → 关 WS(1001) → server.close → 兜底 5s 强退。
- 可观测：结构化 JSON 日志（ts/level/module/msg/data），按模块命名空间。

## 测试策略

- 单元：房间状态机全行为、协议校验、限流器、TTL-LRU、LRC 解析（**直接复用小程序源码测试**）、同步时钟换算、mock 源与门面缓存。
- 集成：`createApp()` 起真实 HTTP+WS，双客户端全链路（建房→加入→握手→点歌→控制→自动接歌→聊天→权限→房主迁移→重入）+ 异常路径（坏令牌/坏消息/限流/人数上限）。
- Live：真实音源搜索→取流→HEAD 验证音频可达→歌词。
- 门禁裁决器 `scripts/verify.js` 汇总为 10 道门禁，exit code 作为唯一达标判据。
